# TypeScript MCP Agent Adapter Plan

**Goal:** expose a user's granted CCP capabilities as MCP tools, so an AI agent can call them while the runtime — not the model — enforces the grant, limits, and confirmation.

**Architecture:** A transport-neutral bridge in `src/adapters/mcp.ts` turns a grant plus verified manifest metadata into MCP tool definitions, then maps each tool call to a freshly signed signal submitted to `Runtime`. The adapter never approves anything: when the runtime requires confirmation it either returns `confirmation_required` to the caller or awaits a host-supplied `confirm` callback. The official MCP SDK is used only by the integration test and the runnable example.

**Tech Stack:** TypeScript 5, ESM, Vitest, `@modelcontextprotocol/sdk` 1.32.x (devDependency only). The adapter itself keeps zero new runtime dependencies and no Node built-ins.

**Spec:** `CCP_Working_Draft_v0.5.md` §10.3–10.4, §11.4, §15.1–15.3, §26.6. Contract: `test-vectors/`.

## Global Constraints

- All 51 frozen vectors and the 122 existing tests stay green.
- `src/` must not import Node built-ins; `src/adapters/mcp.ts` must not import `@modelcontextprotocol/sdk`.
- Adapters never bypass the `Runtime`; they sign a signal, submit it, and relay the decision.
- The adapter must never approve a confirmation on the model's behalf (§15.3). Confirmation is a host decision made from the exact intent, params, and permission card.
- Provider-authored descriptions and tool results are untrusted data (§15.3). The adapter labels provider text and returns results as JSON data.
- Wire fields stay snake_case; TypeScript API names stay camelCase.
- `test-vectors/`, `phase4/`, and `phase4-confirm/` are untouched.
- Commit only when the user asks. The example uses `.ts` specifiers internally because Node type stripping does not resolve `.js` to `.ts`.

## Design decisions

- **Agent-side bridge.** The MCP server runs with the user's runtime and the agent's signing key. The model calls a tool; the bridge signs the signal; the runtime decides. A provider-side MCP tool would have to trust an unsigned tool call, which CCP rejects.
- **One bridge per grant.** The grant is the agent's whole authority. Multiple grants compose by creating multiple bridges, not by widening one.
- **Verbatim intent names.** MCP tool names allow dots, and reusing the intent avoids a mapping table, collisions, and ambiguity in logs.
- **Plain JSON Schema.** CCP schemas are already the strict JSON Schema subset. The low-level MCP `Server` accepts them directly; the high-level `McpServer.registerTool` expects Zod and would require a lossy translation.
- **No auto-approval.** Without a `confirm` callback the tool returns `confirmation_required` with the pending id and card. With one, the host decides; a thrown callback counts as denial.
- **Results as data.** Success returns the schema-validated result as JSON text, plus `structuredContent` only when the intent declares an output schema (MCP requires structured content to conform).
- **Fail fast at construction.** A grant bound to another key, a missing manifest, an undeclared intent, or an unregistered params schema is a configuration error, not a tool error.

### Task 3: MCP bridge

**Files:**
- Create: `sdk/typescript/src/adapters/mcp.ts`
- Create: `sdk/typescript/test/adapters-mcp.test.ts`

**Interfaces:**

```ts
createMcpServer({
  runtime: Runtime;
  agent: Agent;
  grant: Grant;
  manifest?: VerifiedManifest;          // defaults to runtime.manifests.get(grant.manifest_digest)
  confirm?: (request: ConfirmationRequest) => boolean | Promise<boolean>;
  requestTtlSeconds?: number;           // default 60
  now?: () => string;                   // default runtime.clock
}): { tools: readonly McpTool[]; callTool(name: string, args: unknown): Promise<McpToolResult> }

interface McpTool { name; description; inputSchema; outputSchema? }
interface McpToolResult { content: { type: "text"; text: string }[]; structuredContent?; isError? }
interface ConfirmationRequest { pendingId; requestId; intent; params; card }
```

**Behavior:**
- Construction throws when the grant is not bound to `agent.keyId`, the manifest is missing, an intent is not declared, or a params schema is not registered.
- `callTool` rejects an unknown name with `intent_not_allowed`, and non-object arguments with `invalid_request`, as `isError: true` results. It never throws.
- Every call signs a fresh signal (`request_ttl` seconds) and submits it to the runtime.
- `authorized` → JSON text of the result; `structuredContent` only if the tool has an output schema and the result is a non-array object.
- `confirmation_required` without `confirm` → `isError` with `outcome`, `pending_id`, and `request_id`.
- `confirmation_required` with `confirm` → await the decision; approve calls `runtime.confirm(id, true)`, deny calls `runtime.confirm(id, false)`; a thrown callback counts as denial. Denial yields `outcome: "cancelled"`.
- Any other decision → `isError` with `outcome` and, for real §10.4 codes, `error`.

Signal construction:

```ts
const requestId = randomId();
const issuedAt = now();
const expiresAt = new Date(Date.parse(issuedAt) + ttl * 1000)
  .toISOString().replace(/\.\d+Z$/, "Z");
const signal = agent.signalFor({ intent: name, params }, grant, {
  requestId, issuedAt, expiresAt,
});
const decision = runtime.submit(signal, agent.publicKey);
```

Result helpers:

```ts
function success(tool: McpTool, result: unknown): McpToolResult {
  const content = [{ type: "text" as const, text: JSON.stringify(result) ?? "null" }];
  const structured =
    tool.outputSchema !== undefined &&
    result !== null && typeof result === "object" && !Array.isArray(result);
  return structured
    ? { content, structuredContent: result as Record<string, unknown> }
    : { content };
}

function failure(code: string, extra: Record<string, unknown> = {}): McpToolResult {
  const body = {
    outcome: code,
    ...(ERROR_CODES.has(code) ? { error: code } : {}),
    ...extra,
  };
  return { content: [{ type: "text", text: JSON.stringify(body) }], isError: true };
}
```

Denial path: `runtime.confirm` returns `cancelled`, which is not an §10.4 error, so `failure("cancelled")` emits `outcome` only.
